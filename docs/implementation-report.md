# Peterborough Weather upgrade — implementation record

Implemented against the existing repository on 21 October 2026. This record describes the local implementation and checks, not a claim that the new code or optional collectors have been published. No backend, proxy, paid service, trial or card-based plan was added. The GitHub repository was confirmed public with Pages enabled. Existing `CachedRun` records, `buildLatestIndex` and `getRunTasks` public signatures are retained; UKV's `isOverlay` flag remains unchanged for Trends.

## Phase 0 — foundation and probes

Files: `scripts/probe-sources.ts`, `scripts/probe-browser.ts`, `src/data/{probes,contracts,resource,scheduler}.ts`, `src/views/SourceProbe.tsx`, `src/api/{db,fetch,monthly,seasonal}.ts`, `public/sw.js`, `tests/{cacheBudget,migration,serviceWorker}.test.ts`, `tests/fixtures/live/*`, `docs/{capabilities.md,browser-probes.json,request-budget.json}`.

- Node probes save original successful response bodies and JSON sidecars containing URL, parameters, retrieval time, response status/headers, identity, schema, units, time range, null counts and representative values. Failure sidecars retain HTTP errors. Synthetic unit/browser inputs are labelled separately.
- Browser probes established the actual `https://fenlanddavid.github.io` origin using the published page, then read source bodies with JavaScript. The old app's scripts were blocked to avoid its background requests. A successful body read, rather than inspection of an exposed CORS header, determines access. AviationWeather is excluded from browser probes.
- See the model × variable capability table. Confirmed ensemble IDs are exactly `ecmwf_ifs025`, `gfs025`, `ukmo_global_ensemble_20km`. Each model/variable was probed separately; exact production combined nine-day requests were also saved. There is no `best_match` substitution and no claim that a historical `fetchEnsembles` existed.
- Database v3 → v4 adds `ensembleSnapshots`, `datasets`, and a bounded short-lived cross-tab response cache. Existing runs and any legacy stores survive. A v1 wind-unit uncertainty marker preserves old records while excluding their unsafe wind values. Blocked upgrades surface an application status; connections close on version change, and delayed openings close after timeout.
- New calculations use UTC epoch milliseconds, Celsius, m/s, mm water-equivalent, cm snowfall, metres and fractions. `latestDisplayToCanonical` explicitly adapts the existing mph `LatestIndex`; raw `CachedRun` values are already m/s. Local calendar/event windows use Europe/London per instant, including 25 October's repeated hour.
- Changing static JSON/TLE files use network-first fetch with a five-second timeout, validated content and cached fallback under the deployment base. HTML/SPA fallbacks cannot poison the data cache. Lazy JS/CSS assets remain in the installation manifest and precache.
- All application Open-Meteo requests, including manual refresh, Single Runs, seasonal/monthly and optional sky/AQ, use the scheduler. Node probe diagnostics are deliberately separate live-network tests with an explicit Origin header. The scheduler records HTTP attempts separately from conservative weighted reservations, uses Web Locks plus shared response caching, deduplicates in flight, times out, applies bounded retries and Retry-After/429 backoff, and stops optional/all requests at 1,500/2,000 daily weighted calls. Minute ceiling: 300. Older usage entries compact into daily endpoint buckets. If persistent storage is unavailable, a tab can only retain its meter in memory; other devices and lost browser storage are outside this local meter's knowledge.

Checks: migration from v3, blocked connection/versionchange, caching after failed refresh, unavailable storage, 404/400/429/network/schema statuses, in-flight coalescing, minute/daily guard and backoff, changing-file update/HTML rejection, and production browser offline/base-path checks.

## Phase 1 — forecast signals and ensembles

Files: `src/forecast/{ensembles,events,signals}.ts`, `src/hooks/useEnsembles.ts`, `src/components/ForecastEvidence.tsx`, `src/metrics/{forecastSummary,hourlyWeather,utils}.ts`, `src/views/{Forecast,Summary}.tsx`, `src/api/runSchedule.ts`, `tests/{ensembles,signals,cohorts,forecastSummary,runSchedule}.test.ts`.

- Real response counts: IFS 51, GEFS 31, MOGREPS-G 18 for temperature, precipitation, gusts, snowfall and cloud. The plain variable column is member/control 0. Zero-padded member suffixes and a duplicate control alias are recognised; conflicting aliases, invalid units, malformed lengths and non-hourly/duplicate times are rejected.
- The real IFS precipitation fixtures contain twelve negative cells in four members. Those cells become **unknown**, with parser warnings; they never become zero or dry outcomes. Eligibility is recalculated per variable/window. At least 80% of a system's expected members must provide the complete window. Counts and partial states remain visible.
- Current/previous distinct snapshots are separate from deterministic history. Content hashes prevent identical re-downloads creating changes. Confirmed provider metadata avoids repeat downloads of unchanged cycles after the documented propagation allowance. Its latest initialisation is displayed as metadata; the API response itself does not confirm a run ID, so response `issuedAt` remains null.
- Events aggregate **inside members/models first**, with preceding-hour accumulation intervals for precipitation/snow and gust periods. Local days can be 23/24/25 hours. Frost uses 18:00–09:00. Rain/snow 3h, optional 6h, daily precipitation, snowfall, gust, frost and point cloud definitions share one module. Point cloud uses strictly below 30%.
- Ensemble systems receive equal total weight. Expected amounts include dry outcomes; conditional wet medians use equal system weight distributed among eligible members and renormalised over wet outcomes. Empty/insufficient cohorts return null, while eligible all-dry cohorts return probability zero and no conditional wet amount.
- Deterministic families receive equal total influence, split among eligible models, including UKV only where its timestamps/non-null values support the window. There is no AI-model exclusion: the actual AIFS/AIGFS gust columns in the Single Runs probe are all-null and are therefore ineligible, while their supported precipitation remains eligible. UKV had 55 finite temperature/cloud hours in the probed run; that observed range is not hard-coded. The newest run and up to three previous distinct runs provide forecast-only indexed gap filling with actual provenance, including earlier hours needed for a whole-today cohort. The public LatestIndex retains its existing newest-plus-previous contract. Stale known runs are excluded from new event recommendations; cached figures can still display with a stale explanation. Daily complete-window cohorts prevent hour-to-hour changes in the contributing set from producing a fabricated total/extreme.
- Up to four raw runs per model contribute to recent-run support, using a 12-hour half-life and a 36-hour cutoff, normalised within model and then family. Latest agreement and recent support are both shown; neither is called a calibrated probability. Trends remains independent.
- Forecast and Summary consume the same briefing, day condition, thresholds and event semantics. Event percentage displays truncate at the integer boundary and show <1% for small non-zero values, so a possible tier cannot display as 60% likely and a small risk cannot disappear. Non-zero risk survives rounded small amounts, missing cloud does not imply sun, and supported fog/thunder/freezing signals are retained. Early alerts distinguish two-model/two-family consensus from isolated signals; later alerts use explicit ensemble event periods and thresholds.

Checks: real member fixtures for every variable/system; control aliases; deterministic-only rejection; eligibility/nulls; timing-independent event totals; hourly boundaries; maxima/minima; system weights and even-sized wet medians; snapshot rotation; UKV/Trends separation; family/run influence; gap-fill provenance; daily cohorts; shared summary/icon semantics; 23/25-hour days.

## Phase 2 — Night Sky core

Files: `src/astro/ephemeris.ts`, `src/sky/{weather,scoring}.ts`, `src/hooks/useVisibleResource.ts`, `src/views/NightSky.tsx`, `src/views/NightSky.css`, `src/App.tsx`, `tests/{astronomy,sky}.test.ts`, `tests/fixtures/reference/*`, `public/THIRD_PARTY_NOTICES.txt`.

- Pinned MIT libraries: Astronomy Engine 2.1.19; satellite.js 7.1.0. Night Sky is lazy. The production Forecast import graph contains neither astronomy nor satellite propagation. Offline installation precaches both lazy tab chunks.
- Observer: 52.5736°N, −0.2400°E, 10 m above sea level, zero height above ground, unobstructed mathematical horizon. Rise/set includes upper-limb/standard refraction; −6/−12/−18° twilight boundaries use the geometric Sun centre. Library event searches provide boundaries; ten-minute samples do not round event times. Each night belongs to its evening date, local noon to next local noon, and remains the previous observing night after midnight until sunrise.
- Moon illumination is calculated at each sample and at 22:00 for the headline, with geometry-based waxing/waning and a matching disc. No rise/set in the bounded night stays null. Deep-sky mode falls back to nautical darkness in summer, explains twilight and cannot be Excellent without true darkness.
- Sky data is requested only on Night Sky entry/expiry: three explicit models, ten core variables plus separate optional visibility/250 hPa requests, one-hour cache. IFS visibility was all-null without a useful unit, so it is deliberately not requested in the production optional group. UKMO has genuine trailing gaps. CAMS global AOD/dust has a separate six-hour cache and finite seven-day requested axis; values are never extrapolated beyond their actual non-null coverage. Optional variable provenance remains separate from core response provenance. Additional deterministic models, including UKV, can contribute canonical cached cloud/gust core values within their actual range. Their missing layers, dew point, visibility and jet data remain unknown, rather than being borrowed from another model/run; all-null AI gusts naturally prevent an observing score without excluding supported AI precipitation.
- Remembered deep-sky and Moon/planets modes use the specified cloud overlap, Moon, transparency, gust and precipitation heuristics. Cloud/transparency/fog/gust nonlinear components are evaluated per model before family combination. Missing core inputs break scores/windows; missing transparency components are listed, never called Good. AOD is a separate CAMS context input; dust is not scored.
- Windows use elapsed duration and actual darkness boundaries, including partial first/last intervals and repeated local clock hours. Current-night recommendations exclude elapsed time. Full-night ratings need 75% coverage; best-night ranking also needs that coverage from at least two families. The hourly strip averages ten-minute eligible samples; the underlying windows never bridge missing samples. Dew, equipment frost, radiation-fog support and jet guidance retain model-level disagreements.

Checks: USNO independent Sun/Moon rise/set and civil-twilight references (90-second tolerance); JPL independent Jupiter position (0.02°) and apparent magnitude (0.05 mag); correct noon-vs-22:00 illumination semantics; waxing/waning; June absence of astronomical darkness; bounded no-rise/no-set; repeated hours/after-midnight identity; nonlinear score and unit boundaries; fog disagreement; missing optional/core inputs; dawn/current-time clipping; duration/coverage/rating ties; incomplete final nights.

Limitations: score thresholds/overlap are unverified planning heuristics. The API does not identify the actual sky response issue time; fetch age and coverage are shown rather than inventing one. Pressure-level wind is only one atmospheric indicator. Independent references cover selected fixed dates/definitions, not every event or real horizon. Weather may be interpolated from coarser native model steps; ten-minute astronomical scoring is not ten-minute weather forecast skill.

## Phase 3 — aurora

Files: `src/sky/aurora.ts`, `src/components/AuroraPanel.tsx`, compatibility facade `src/api/aurora.ts`, `tests/aurora.test.ts`, real NOAA/AuroraWatch fixtures, optional collector described below.

- Current estimated decimal Kp is preferred, with an integer fallback. Observed, estimated and predicted blocks remain distinct; NOAA's current `predicted` field maps to forecast. Three-hour block starts are intersected with actual civil darkness for the selected night. Current activity, next few hours, this night's dark blocks and later selected nights do not use a 72-hour maximum as tonight's headline.
- Old two-hour magnetometer/plasma products returned Node 404 and unreadable browser fetches. NOAA's published 2026 service change identifies `json/rtsw/rtsw_mag_1m.json` / `rtsw_wind_1m.json` as replacements. Their real fixtures expose explicit GSM/GSE fields and active spacecraft. Only active quality-zero GSM Bz samples qualify; speed retains its independent time/source.
- Sustained southward Bz needs the specified ≤−10 nT, 30-minute coverage, no >5-minute gaps, ≥80% coverage, fresh samples and local darkness. It is labelled a favourable solar-wind condition, not proof of visible aurora.
- OVATION validates source observation/forecast times and wrapped grid longitudes. Its 55–60°N regional range is explicitly a source-grid context, never Peterborough's visibility probability.
- AuroraWatch HTTPS XML is browser-readable at the deployed origin. The original colour and paraphrased upstream UK meaning are shown, with Lancaster/SAMNET/AuroraWatchNet links. An optional static fallback remains available. Freshness uses the upstream timestamp, including after downloading unchanged old data.
- Night Sky polling stops when hidden/unmounted. Kp checks use 30 minutes; OVATION, RTSW and AuroraWatch use ten minutes. Each source retains its own errors and successful cache. Stale/unknown source age suppresses real-time prompts.

Checks: actual decimal/predicted schemas; invalid Kp; daylight removal; stale source age; longitude wrapping; regional labels; active GSM parsing; Bz gaps/northward/coverage/daylight vetoes; AuroraWatch XML/status/time validation.

## Phase 4 — events and ISS

Files: `src/astro/{ephemeris,iss,events}.ts`, `src/components/SkyEventsPanel.tsx`, `tests/astronomy.test.ts`, `vite.config.ts`.

- Planet positions, refined altitude maxima/directions and apparent magnitudes are calculated for Mercury through Saturn; only planets exceeding 10° in the relevant dark interval are included. Rise/set is bounded to the observing night and explicitly handles already-up/no-event cases.
- Seasons are computed, not approximate annual dates. Eclipse searches cover the next 12 months; solar circumstances are local, and lunar/solar portions are clipped/refined against the local horizon. Global occurrence alone is insufficient.
- The maintained meteor table is retained as approximate annual guidance. It no longer asserts an unverified year-specific “peak tonight”; Moon conditions and the computed weather window accompany it. Zodiacal light suggestions require a moonless astronomical-dark usable window lasting at least two hours.
- CelesTrak's real response is a checksum-validated NORAD 25544 TLE. SGP4 and the library's solar-disc shadow calculation require ≥10° elevation, Sun below −6°, and ≥99% unshadowed solar disc. The 20-second search refines visible boundaries to half a second and the visible peak to one-second sampling, then displays minute-level times. Element epoch remains visible; predictions stop at epoch +72h and old elements suppress the entire forecast. Browser cache: 12h.
- satellite.js 7.1.0 re-exports unused WASM workers from its package barrel, which Vite scans before tree shaking. A version-pinned Vite transform removes only that unused export; the supported JS functions remain lazy. Build tests guard the result. No external worker/service was introduced.

Checks: independent fixed-date Jupiter reference; local eclipse portions; real TLE/checksum; stale/future/epoch horizon; visible ISS peaks must meet darkness/elevation/sunlight; lazy production/offline chunks. ISS minute predictions have not been independently compared against an observed pass; actual obstructions, orbit manoeuvres and atmospheric conditions remain limitations.

## Phase 5 — optional observations and verification

Files: `scripts/collect.ts`, `src/verification/verification.ts`, `src/components/VerificationPanel.tsx`, `src/views/Trends.tsx`, `tests/verification.test.ts`, `.github/workflows/{collect-data,deploy}.yml`, `public/data/{obs,verification}/*`, `public/data/{aurorawatch.json,iss-tle.txt,iss-tle.meta.json}`.

- Collectors are optional/independent and default disabled until public repository variables enable them. The local smoke run saved real source data without enabling schedules or publishing anything. No user API secret is needed; GitHub's built-in scoped workflow token performs archive commits/Pages deployment.
- AviationWeather currently documents 30-day retention, a typical 400-row response cap and 100 requests/minute, with no browser CORS. One-station one-day queries, 700ms minimum spacing, watermark overlap, raw report identities and atomic writes recover bounded missed periods without replacing good archives with empty failures.
- Observed EGXT coverage: 1,428 reports from 21 September 20:20 UTC through 21 October 18:20 UTC; 31 boundary-inclusive UTC dates, including eight weekend dates and 715 reports in UTC 18:00–06:00. Most complete dates had 48 reports; examples of actual gaps are retained. This confirms sampled overnight/weekend reporting, not a guarantee of continuous future coverage.
- Forecast verification requests use the observed station (52.611, −0.461, elevation 74m), retaining returned grid/elevation metadata. Fixed Previous Runs offsets are 24/48/72/120/168h. Unsupported/horizon-null outputs are excluded. The seed has 25 temperature model/lead score series over roughly eight dates, not enough training history for a correction proposal.
- Matching selects one nearest report per station/UTC hour within 30 minutes, with deterministic METAR/SPECI tie handling and signed offsets. Missing gusts and variable wind remain missing/variable. Metrics are MAE/MSE/forecast-minus-observation bias; date counts and training/hold-out boundaries use UTC consistently.
- Overall temperature-only proposals require ≥200 paired hours across ≥20 training dates, use the preceding 30 training days and seven subsequent held-out dates, subtract capped ±3°C bias, and retain held-out raw/proposal/equal-family baseline results. The day/night subset gate is implemented for future subset proposals (100/15 each); this release produces overall proposals only. All corrections, automatic weighting and station-to-Peterborough transfer are disabled.
- Sustained-wind scoring remains disabled until the source/model averaging definitions are demonstrably compatible. No rain Brier score is produced from METAR weather codes, and airport cloud categories are not treated as exact column cloud percentages.

Checks: real METAR normalisation, raw/station/missing fields, nearest-hour offsets and deduplication, location separation, signed metrics, empty data, sample/date gates, held-out chronology/baseline, bias caps and disabled application flags.

## Static publication and optional collector operation

Repository settings variables: `COLLECT_METAR`, `COLLECT_VERIFICATION`, `COLLECT_AURORAWATCH`, `COLLECT_ISS` = `true` selectively. The workflow runs hourly at :17 when enabled on a public repository; scheduled timing is not assumed exact. Run `Deploy GitHub Pages` once with this implementation before enabling the collectors.

The full app deployment retains a `site-shell` artifact. The collector serialises archive writers, commits changed files and uploads a data-only artifact. A separate Pages job restores the most recent completed app shell, overlays new data, and deploys that static artifact. It does **not** rebuild the application hourly. A `public/data`-only commit is ignored by the main app build workflow. A missing/failed shell deployment stops publication visibly and preserves committed data; a commit is not proof that Pages deployed. Check the collector Pages job and the deployed files' source timestamps to verify delivery. Existing cached data remains usable if collectors are disabled, delayed or fail.

GitHub-side scheduling, repository-variable configuration, artifact retention expiry and the final data-only deployment have not been exercised remotely in this task. The local collector and source/browser/worker paths were exercised. No claim of live release is made.

## Measured impact and verification artefacts

- `request-budget.json` is produced from the actual `getRunTasks` plan and verified endpoint cost function. The 24-hour cold-start scenarios reserve **644 / 788 / 860 weighted calls** for 0/6/9h deterministic publishing lags, including twelve visible Night Sky hours, all outlook requests and four distinct ensemble cycles. They are explicit simulated request plans, not a claimed network worst case. Retries/fallbacks each consume meter reservations; hard local limits supersede the plan. Ensemble downloads reserve 26/16/9 calls; metadata HTTP requests have the documented zero weighted cost.
- `bundle-report.json` records exact production bytes/gzip and checks the initial static graph. Baseline initial JS was 338.79kB (103.35kB gzip); the final initial JS is **329.36kB** (Vite reports 102.93kB gzip), with a **129.70kB** lazy Night Sky chunk (53.82kB Vite gzip). Both libraries remain outside the initial execution graph. Offline installation downloads all lazy JS in the background: 858.09kB total JS versus the 730.83kB baseline, an increase of about 127.26kB. The JSON report also records Node gzip measurements with its own stated compression method. The lazy Night Sky chunk includes its UI and both libraries; no per-library byte saving is claimed.
- `browser-probes.json`: real deployed-origin CORS/readability checks. `browser-smoke.json`: mobile assembled-fixture app integration, shared cache/no duplicate core URLs, Summary ensemble semantics and offline Forecast/Night Sky/Trends. The latter tests wiring and offline assets, not live forecast skill.
- Deterministic unit tests are separate from live probes. Run `npm test`, `npm run test:timezones`, `npm run lint`, `npm run check:scripts`, `npm run build -- --base /peterborough-weather/`, then `npm run report:bundle`. Browser scripts accept `CHROMIUM_PATH`; no browser binary is downloaded by the dependency installation.
